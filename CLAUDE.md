# CLAUDE.md

Инструкции для Claude по ведению этого репозитория. Требования и роадмап — в [docs/PRD.md](docs/PRD.md).

## Суть проекта

MLQA — библиотека реальных вопросов с собеседований на ML-позиции (DS, ML/AI Engineer, NLP, LLM, RecSys, CV, HFT и т.п.). Сайт — статический, на GitHub Pages: https://aimnoux.github.io/mlqa/

Главная задача Claude — **поддерживать базу**: принимать материалы собеседований, выписывать вопросы, сверять их с базой без дублей, считать упоминания и писать теорию к новым вопросам.

## Язык

- Всё содержимое, коммиты, README и документация — **на русском**.
- На латинице только идентификаторы: `id` вопросов, разделов, тем, собеседований, имена файлов и полей.
- Общепринятые термины не переводим: attention, dropout, batch norm, LoRA, KV-cache.

## Модель данных

**Вопрос** — один концепт, который раскрывается одной статьёй с теорией. Поля — в `templates/question.md`. Ключевые правила:
- `id` = имя файла, kebab-case, на английском, по смыслу (`self-attention`, `bias-variance-tradeoff`). **Не переименовывать**: на нём держатся URL и ссылки из собеседований.
- `title` — каноническая формулировка вопроса по-русски.
- `aliases` — другие реальные формулировки. Каждая новая формулировка с собеса, которая заметно отличается от уже имеющихся, добавляется сюда.
- `parent` — id родителя, если это уточняющий вопрос. Вложенность — **максимум один уровень**: у уточняющего вопроса не бывает своих уточняющих.
- `status`: `todo` → `draft` → `done`.

**Собеседование** — поля в `templates/interview.yaml`. Список `questions` повторяет реальный ход собеса: `q` — id вопроса, `asked` — формулировка, `followups` — уточнения.

**Упоминания не хранятся в вопросах** — они вычисляются: `mentions(q)` = число собеседований, где встретился `q` (в основном списке или в `followups`). Если в одном собесе вопрос прозвучал дважды, это одно упоминание.

## Процесс: обработка нового собеседования

Пользователь присылает видео, аудио, транскрипт или готовый список вопросов, а также метаданные: роль, грейд, дату, этап, компанию (можно не указывать).

1. **Сохранить материал в `inbox/`.** Если метаданных не хватает — спросить; то, что неизвестно, записать как `unknown`/`null`.
2. **Получить текст.** Видео и аудио → транскрипт (`scripts/transcribe.py`, faster-whisper, `language=ru`). Если транскрибировать в контейнере не получается (нет ffmpeg, слишком долго, слишком большой файл), попросить пользователя прислать аудио или транскрипт, см. PRD §6.
3. **Выписать вопросы.** Только технические, включая технические вопросы про проекты кандидата. HR-вопросы и вопросы в духе «расскажи о себе» пропускаются. Для каждого вопроса фиксируется близкая к оригиналу формулировка и уточнения, прозвучавшие после него. Задачи live-coding записываются как вопрос о том, какие знания нужны для решения (алгоритм, приём), а не как текст задачи целиком.
4. **Сопоставить с базой** — главный шаг, см. «Правила дедупликации». Для каждого вопроса результат один из трёх: *существующий*, *новый*, *уточняющий к существующему*.
5. **Записать собеседование** в `content/interviews/<YYYY>/<id>.yaml`.
6. **Обновить вопросы:** добавить новые формулировки в `aliases`, создать файлы для новых вопросов, обновить `updated`.
7. **Написать теорию** для новых вопросов (статус `draft` или `done`). Если вопросов много, сначала создаются файлы со статусом `todo`, а теория пишется следующим коммитом.
8. **Проверить** (см. чеклист), обновить статистику в README, закоммитить.
9. **Отчитаться пользователю:** сколько вопросов извлечено; сколько новых, существующих и уточняющих; спорные случаи сопоставления.

## Правила дедупликации

Перед созданием вопроса **обязательно** искать похожие по `title`, `aliases` и `tags` во всём `content/questions/`: grep по ключевым словам на русском и английском, включая синонимы. После M3 для этого будет `scripts/find_similar.py`.

- **Тот же вопрос**, если для ответа нужна та же теория, даже если формулировки разные («Что такое переобучение?» ≈ «Как понять, что модель переобучилась?»). → Добавить `alias` и записать упоминание.
- **Уточняющий**, если это узкий аспект более общего вопроса и обычно звучит после него («Зачем делить на √dₖ?» после «Как устроен self-attention?»). → Отдельный файл с `parent`.
- **Отдельный вопрос**, если нужна существенно другая теория, даже если тема близкая («L1 vs L2 регуляризация» и «Что такое dropout» — разные вопросы).
- Слишком широкий вопрос («Расскажи про трансформеры») сопоставляется с самым близким обзорным вопросом. Если такого нет — создаётся обзорный вопрос, а конкретика уходит в уточняющие.
- **Слияние дублей**, найденных позже: оставить вопрос с более ранним `created`, перенести `aliases` и теорию, заменить id во всех `content/interviews/`, удалить дубль. После M2 добавить редирект в `mkdocs.yml`.
- Если сомневаешься, спроси пользователя, а не создавай дубль.

## Как писать теорию

Структура — в `templates/question.md`. Принципы:
- **Теория, а не ответ для собеса.** Не «скажите интервьюеру, что…», а объяснение, как всё устроено. Цель: читатель ответит своими словами и выдержит уточнения.
- Порядок: интуиция и зачем это нужно → как устроено → формулы → почему именно так → ограничения.
- Глубина соответствует `difficulty` и тому, куда обычно уходят уточнения. Не пересказывать учебник целиком: пререквизиты оформлять ссылками на другие вопросы.
- Формулы — LaTeX (`$...$`, `$$...$$`), код — Python, если вопрос не про другой язык.
- Каждое утверждение должно быть проверяемым. Никаких выдуманных цифр и ссылок: в «Источниках» только реально существующие статьи и книги. Если не уверен, лучше не указывать.
- Ссылки на другие вопросы — относительные пути к `.md`.

## Таксономия

- Раздел и тема вопроса определяются по **смыслу**, а не по роли, на которой его задали.
- Если тема подходит к нескольким разделам, выбрать ту, где читатель будет искать в первую очередь, а связь выразить через `tags` и `related`.
- Новую тему в `taxonomy.yaml` заводить, когда набирается 3+ вопроса, не ложащихся в существующие. Новый раздел — только после согласования с пользователем.

## Чеклист перед коммитом

После M1 это делает `python scripts/validate.py && python scripts/stats.py`. До тех пор проверять вручную:
- `id` уникальны и совпадают с именами файлов; раздел и тема из пути есть в `taxonomy.yaml`.
- Каждый `parent`, `related` и каждый `q` в собеседованиях ссылается на существующий вопрос; у уточняющего вопроса нет своего `parent`-потомка.
- Блок `<!-- STATS:START -->…<!-- STATS:END -->` в README обновлён.
- В коммит не попали файлы из `inbox/`, медиа или транскрипты.

## Коммиты

На русском, с префиксом:
- `ingest: <id собеса> (+N новых, M существующих, K уточняющих)`
- `theory: <id вопроса>` или `theory: N вопросов по <теме>`
- `content:` — правки существующих вопросов, слияние дублей
- `taxonomy:`, `site:`, `scripts:`, `docs:`

## Нельзя

- Коммитить сырые материалы: видео, аудио, транскрипты и любые файлы из `inbox/`.
- Коммитить персональные данные: имена кандидатов и интервьюеров, контакты. Компанию указывать только если пользователь не против.
- Править блок статистики в README вручную, когда уже есть `scripts/stats.py`.
- Хранить счётчик упоминаний в файлах вопросов.
- Переименовывать `id` вопросов.
